# PQ devnet-0 validator and genesis setup

This branch proposes with the full depth-31 Keccak-256 VRF tree from [consensus-specs `2f43bc0`](https://github.com/ethereum/consensus-specs/blob/2f43bc0f989f47af81df390a90bc1f78e2436323/specs/_features/pq/validator.md#vrf-tree). Use a fresh genesis with full-tree roots and matching precomputed data. The older padded genesis and overlay belong to the `pq` branch.

The BLS keystore still provides the signing secret for `SHA256("vrf-seed" || bls_secret_key_bytes)`. Lighthouse derives the first `2^20` leaves locally and completes their proofs using the upper 11 siblings from the precomputed state. It validates all 31 siblings of the slot-zero record and authenticates the record against the validator’s on-chain root. It uses the same beacon endpoint to verify the VC’s genesis validators root and resolve the derived XMSS validator identity. The precomputed data covers slots 0 through `2^20 - 1`. Proposals at later slots require artifacts and software that cover additional subtrees.

## Validator client

Use `--vrf-state-url` with an HTTP(S) URL, absolute or relative local path, or `file://` URI. The artifact is a concatenation of 1,028-byte records. Each contains a 32-byte root, a four-byte little-endian slot field set to zero, and 31 32-byte siblings from leaf to root. The record offset uses the EIP-2334 index in `m/12381/3600/<index>/0/0` from the voting keystore. The validator’s index on chain can differ. For keystores with no path, including those generated by the pinned Kurtosis package, the VC finds the unique record that matches the validator’s registered VRF root. This uses the full artifact. Malformed paths, duplicate derivation indices among enabled keystores, and missing or ambiguous root matches prevent the affected validators from proposing.

With an index, the client reads the record with an HTTP Range request or local file seek. When a path is absent or the server ignores Range, the client reads up to 10,000 records and shares one copy of the complete artifact across all keys. Verified records are also cached under `vrf-state-cache` in the validator directory, and a restart revalidates them against the beacon node and the local key. A missing, invalid or unavailable record prevents block production for the affected key.

## Kurtosis

Use [ethereum-package `f6c5e11`](https://github.com/ethpandaops/ethereum-package/tree/f6c5e11f7fc2c0d23cb29735a2ffcba7d43c8f0e) or a later compatible release. This package already uses `lighthouse-pq-bn` for the beacon node and supports `vrf_state_url` for Lodestar and Consensoor. Use the new devnet-0 Lighthouse image for both the beacon node and validator client. That image must include `leanvm-sidecar` built at `283686575c4e81790591d2c6e3ed21c69c0e3bbe` and the [Lighthouse prover supervisor](lighthouse-pq-bn).

With the package’s default publicly known devnet mnemonic, merge the settings below into a copy of your existing network YAML. Keep all participant settings and add the VC argument only to Lighthouse participants. `xmss_pubkey_url` supplies the matching full-tree registry entries for fast genesis generation. Custom mnemonics require their own genesis key/root records and VRF artifact.

```yaml
network_params:
  pq_fork_epoch: 0
  xmss_pubkey_url: https://raw.githubusercontent.com/ethpandaops/ethereum-package/d4c9a8ace9dd80ca4f9938885345f8f40a646fd0/static_files/xmss-keys
  vrf_state_url: https://raw.githubusercontent.com/ethpandaops/ethereum-package/d4c9a8ace9dd80ca4f9938885345f8f40a646fd0/static_files/xmss-keys/b9dec4e1daa17dfe.vrf

ethereum_genesis_generator_params:
  image: ethpandaops/ethereum-genesis-generator:pq@sha256:296c352575e5d6cb2bf22e179165f21c39a8114f27804540c2b84bf806820e33
```

```yaml
# In each Lighthouse participant entry, append to vc_extra_params:
vc_extra_params:
  - --vrf-state-url=https://raw.githubusercontent.com/ethpandaops/ethereum-package/d4c9a8ace9dd80ca4f9938885345f8f40a646fd0/static_files/xmss-keys/b9dec4e1daa17dfe.vrf
```
